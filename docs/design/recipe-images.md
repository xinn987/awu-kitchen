# 食谱图片首版设计

## 1. 设计目标

图片只解决两个真实问题：

1. **主图**帮助家人识别“做成后大概是什么样”。
2. **步骤图**帮助家人理解某一步仅靠文字难以表达的状态、质地或动作。

图片不是正式收录门槛，也不替代食谱名称、成功关键或步骤文字。产品的核心仍是可复用的家庭成功经验，而不是图片展示或菜谱相册。

## 2. 首版边界

### 2.1 支持

- 每份食谱最多一张主图，可选。
- 每个步骤最多一张步骤图，可选。
- 从相册选择或直接拍照。
- 选择后本地预览，保存食谱时统一处理并上传。
- 主图只在详情页展示，食谱库卡片不展示。
- 步骤图紧跟对应步骤文字展示，并支持点击查看大图。
- 修订记录保存图片引用，恢复旧版本时一并恢复当时的图片。
- 旧食谱和旧修订记录无须一次性迁移。

### 2.2 不支持

- 一份食谱多张主图。
- 一个步骤多张图片。
- 裁剪、滤镜、涂鸦和图片说明文字。
- 图片相册、图片搜索和图片排序。
- 快速收录时添加图片。
- 食谱库卡片展示主图。
- 保存原始超大照片。
- 首版物理清理仍被历史版本引用的图片。

## 3. 第一性原则

### 3.1 成功关键优先于图片

阿呜厨房的差异不是“看起来像什么”，而是“怎样才能再次做成功”。因此页面顺序保持：

```text
名称和归因
成功关键
主图（存在时）
食材
步骤及步骤图
```

主图不放到名称之前，也不进入食谱库卡片，避免视觉内容压过家庭经验。

### 3.2 图片必须有明确归属

主图只属于食谱；步骤图只属于一个有稳定身份的步骤。不能用图片数组下标关联步骤，否则删除或移动步骤后容易图文错位。

### 3.3 选择图片不等于保存

选择图片只是编辑状态。只有图片上传成功、食谱版本校验通过并写入数据库后，页面才能提示保存成功。

### 3.4 已进入历史的图片不可随当前版本删除

替换或移除当前图片不能立即物理删除旧文件，因为旧修订记录可能仍在引用。首版保留历史文件，后续只清理没有被任何当前食谱或修订记录引用的文件。

## 4. 领域与数据模型

```ts
interface RecipeImage {
  fileId: string
  width: number
  height: number
}

interface RecipeStep {
  id: string
  text: string
  image?: RecipeImage
}

interface RecipeContent {
  name: string
  successKeys: string[]
  mainImage?: RecipeImage
  ingredients: Ingredient[]
  steps: RecipeStep[]
  stage?: Stage
  type?: FoodType
  tags: string[]
}
```

`RecipeImage` 只保存云文件引用和展示尺寸，不保存 Base64、临时 URL 或本机路径。客户端编辑态可以额外持有本地临时路径，但不能提交给云函数。

### 4.1 旧数据兼容

云端清洗函数同时接受：

```ts
steps: string[]
```

和：

```ts
steps: Array<{ id: string; text: string; image?: RecipeImage }>
```

旧字符串步骤读取时转成可展示的步骤对象；用户下一次确认保存时再持久化稳定步骤 ID。旧修订快照同样按此规则读取和恢复。

### 4.2 步骤身份规则

- 新建步骤时生成随机稳定 ID。
- 上移或下移只改变顺序，不改变 ID。
- 步骤图跟随步骤 ID，不跟随数组下标。
- 删除步骤会同时从当前编辑内容移除其步骤图引用。
- 复制食谱时保留步骤 ID 以外的内容，给副本步骤生成新 ID；图片文件可继续复用同一家庭文件引用。

## 5. 页面交互设计

### 5.1 食谱库

首版无变化：

- 卡片仍突出名称和第一条成功关键。
- 不渲染主图，不触发图片下载。
- 搜索、类型筛选和待补条目不受影响。

这样列表加载速度和当前信息密度都不变化。

### 5.2 快速收录

首版无变化。快速收录继续只询问名称和成功关键；只有名称时可存为待补条目。

图片属于“完善食谱”，不应增加核心收录流程的负担。正式收录后进入详情页，用户需要时再通过底部“完善食谱”添加图片。

### 5.3 编辑食谱

编辑页保持当前分区、色彩和排版，只增加两个图片入口。

#### 主图

主图分区放在“成功关键”之后、“食材”之前：

```text
食谱名称

成功关键 *
[关键经验编辑区]

主图（可选）
[ 添加主图 ]

食材
步骤
分类与标签
```

空状态使用浅暖灰底和细虚线边框，文案为：

- 主操作：`添加主图`
- 辅助说明：`记录做成后的样子`

选择后显示一张 3:2 的圆角预览图，图片下方使用两个低强调文字操作：

- `更换`
- `移除`

不把操作压在图片上，避免在复杂照片上出现可读性问题。

点击添加或更换时调用微信媒体选择器，一次只选一张，并同时允许相册和相机。用户拒绝权限时，在当前页面说明“需要相册或相机权限才能添加图片”，确认后打开微信系统权限设置；不在应用内“设置”页增加重复的权限开关。

#### 步骤图

现有步骤列表继续以“点一行进入编辑”为主。已有步骤图时，在该步骤右侧显示小缩略图；没有图片时不显示占位，避免列表变得拥挤。

步骤编辑条在文字框下增加图片区域：

```text
[步骤文字输入框] [加入/改好]
[ + 添加步骤图 ]
```

输入新步骤时，只有步骤文字非空才允许选择步骤图。点击“加入”时文字和本地图片一起成为新步骤。编辑已有步骤时，该区域显示当前步骤图，并提供“更换”和“移除”。

移动步骤时图片随步骤一起移动；删除步骤时当前编辑内容里的图片引用一起移除，但云文件在保存前不会发生变化。

#### 保存状态

保存流程分为：

```text
确认保存
  → 处理图片
  → 上传新图片
  → 提交食谱和 expectedVersion
  → 服务端确认
  → 返回详情页
```

按钮状态按阶段显示：

- 无新图片：`正在保存…`
- 有新图片：`正在处理图片…`
- 上传阶段：`正在上传 2/4…`
- 数据写入：`正在保存…`

保存期间禁用重复提交、图片操作和返回操作。任何阶段失败都留在编辑页，保留文字和本地图片预览，并显示明确的重试提示。

### 5.4 食谱详情

详情页不增加顶部按钮，底部仍只有“复制”和“完善食谱”。

```text
食谱名称
修改人和修订记录

成功关键
[成功关键内容]

[主图，仅存在时展示]

食材

步骤 1
步骤文字
[步骤图，仅存在时展示]

步骤 2
步骤文字

[复制] [完善食谱]
```

主图使用全宽 3:2 圆角画面，不显示“主图”标题；它是内容本身，不需要额外标签。点击后使用微信图片预览查看完整比例。

步骤区域改为“序号 + 步骤主体”。步骤图放在文字下方、与文字左边缘对齐，使用 3:2 圆角缩略图并开启懒加载。点击任一图片时，可在当前食谱全部图片之间左右浏览。

没有主图或步骤图时不显示空白框、图标或提示，详情页保持现在的纯文字阅读节奏。

云图片暂时加载失败时，在原图片比例内显示浅暖灰错误槽和“重新加载”，不显示系统破图图标，也不影响文字内容继续阅读。

### 5.5 修订记录

时间线首版不直接渲染图片，避免历史页变得过重。修订快照仍保存图片引用；恢复某个版本时，主图和步骤图随该版本一起恢复。

## 6. 视觉规范

沿用当前视觉令牌，不建立新的图片主题：

| 用途 | 颜色/规则 |
| --- | --- |
| 页面底色 | `#F4EFE6` |
| 卡片与图片衬底 | `#FFFFFF` |
| 空图片槽 | `#EDE6DA` |
| 主操作 | `#BF5924` |
| 正文 | `#1A1714` |
| 次要文字 | `#7C6F63` / `#9A8E82` |
| 圆角 | 主图 `28rpx`，步骤图 `22rpx` |
| 边框 | `1rpx solid rgba(26, 23, 20, 0.10)` |

标题和成功关键继续使用现有思源宋体子集；图片操作、进度和辅助文案使用系统无衬线字体。

图片的视觉角色是一张嵌入家庭食谱的“实拍记录”，因此只使用克制的白色衬底、细边框和轻阴影，不使用渐变、彩色遮罩、大图标题或社交媒体式图片卡片。

## 7. 图片处理与性能

- 只上传处理后的展示图，不上传原始照片。
- 长边限制为约 `1600px`，JPEG 质量约 `75`。
- 处理后单张目标不超过 `1.5 MB`；超出时继续降质或提示重新选择。
- 上传并发最多 `3` 张，避免低端手机瞬时占用过高。
- 详情页图片使用懒加载；未滚动到的步骤图不主动下载。
- 食谱库不创建图片节点，因此不会因新增图片改变列表首屏速度。
- 数据库只增加短文件引用，图片二进制不经过 `api` 云函数。
- 选图使用微信提供的压缩图片模式；具体相册、相机接口和隐私声明要求在实施及发布前按当时平台规则核验。

## 8. 云存储与安全边界

- 图片存入当前微信云环境的传统云存储。
- 路径按家庭组织并使用不可预测文件名，例如：

```text
recipe-media/{familyId}/{randomId}.jpg
```

- 文件不可原地覆盖；更换图片总是上传新文件，保证旧修订仍可读取。
- 小程序只能把图片上传到云存储，不能直接修改食谱数据库。
- `recipe.create`、`recipe.update` 和 `recipe.restoreRevision` 继续在云函数中确认当前家庭资格。
- 云函数拒绝不属于当前家庭媒体路径的文件引用，并限制一张主图、每步一张图片和最多 30 个步骤。
- 云存储权限需要在实施时单独核验，不能因为数据库禁止客户端写入就假设文件权限已经安全。

首版的实际隐私边界是：食谱接口只向家庭成员返回文件引用，文件名不可猜。若以后需要更严格的文件撤权或审计，再增加短期访问地址和独立媒体授权接口。

## 9. 一致性与失败处理

图片上传和食谱数据库事务无法天然合并为一个原子操作，因此必须明确以下语义：

1. 本地选择不表示已保存。
2. 所有新图片上传成功前不提交食谱更新。
3. 食谱更新仍使用 `expectedVersion`。
4. 上传失败时不改变云端食谱。
5. 图片已上传但食谱保存失败时，客户端尽力删除本次新文件；清理失败只会产生无引用文件，不会产生错误食谱引用。
6. 替换、移除、删除步骤或归档食谱时，不删除可能仍被修订记录引用的旧文件。
7. 恢复旧版本只恢复文件引用，不重复上传图片。
8. 复制食谱复用家庭内的图片文件，不产生重复文件。

## 10. 实施顺序

1. 增加 `RecipeImage` 和稳定 `RecipeStep`，兼容读取旧字符串步骤。
2. 云函数增加图片字段校验和家庭媒体路径校验。
3. 增加客户端图片处理、上传和失败清理服务。
4. 改造编辑页主图与步骤图交互。
5. 改造详情页主图、步骤图、懒加载和图片预览。
6. 验证修订恢复、复制、删除步骤和版本冲突。
7. 在 iPhone 和 Android 真机验证相册、相机、大图、弱网和中途退出。

## 11. 验收场景

- 无图片的全部旧食谱展示和编辑不变。
- 只添加主图后保存，详情页成功显示，食谱库不下载图片。
- 给不同步骤分别添加图片，重排后图文仍正确对应。
- 删除带图步骤并取消编辑，云端内容不变。
- 替换主图后，当前详情显示新图，旧修订恢复后显示旧图。
- 图片上传失败时文字和本地预览仍在，页面不提示保存成功。
- 拒绝相册或相机权限时有明确说明，并能进入微信系统权限设置后重试。
- 云图片加载失败时文字仍可阅读，原位置可以重新加载。
- 图片上传完成但发生版本冲突时，不覆盖家人的新版本。
- 复制带图食谱后，副本图片可正常显示。
- 归档带图食谱后，正常列表不显示，历史图片不被误删。
- 包含多张步骤图的长食谱只有滚动到附近时才加载图片。
