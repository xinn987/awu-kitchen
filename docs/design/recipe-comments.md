# 食谱评论首版设计

## 1. 设计结论

首版把评论设计为一份食谱的“家庭讨论”，而不是食谱正文的一部分：

1. 食谱详情页不渲染完整评论列表。
2. 在详情页固定底部操作区增加 `评论` 入口，有评论时显示数量。
3. 点击进入独立的“评论”页，集中查看、发布、编辑和删除评论。
4. 评论中的有效结论不会自动修改食谱，需要家庭成员通过“完善食谱”写入正文并形成修订记录。

这样既保证长食谱在任何滚动位置都能进入讨论，又不会让评论继续拉长正文或干扰做饭时阅读。

## 2. 第一性分析

### 2.1 食谱详情页的首要任务

食谱详情页首先要帮助家人快速复现一次成功做法。成功关键、食材和步骤是稳定知识；评论是围绕这些知识产生的临时交流。两者的阅读节奏不同：

- 食谱正文需要稳定、连续、可反复查阅。
- 评论会不断增长，包含提问、尝试反馈和暂未验证的建议。

因此评论不能与正文处在同一个连续信息流里，否则未经确认的意见会和已经验证的做法混在一起。

### 2.2 为什么不放在页面底部

把完整评论区放在步骤之后有三个问题：

- 食谱越详细，评论入口越难发现。
- 评论越多，页面越长，归档和删除入口也会被继续推远。
- 用户只是想评论某一步时，必须先滚过整份食谱。

底部只放一行“查看全部评论”虽然减少长度，但入口依然受正文长度影响，没有解决随时可达的问题。

### 2.3 为什么不使用半屏弹层

半屏弹层适合少量选择，不适合需要键盘、长文本、编辑状态和删除确认的讨论。微信键盘弹出后可用高度更小，评论多时也不利于持续浏览。独立页面的返回关系清楚，真机交互更稳定。

### 2.4 为什么放在固定底部操作区

当前详情页已经把业务操作集中在底部，顶部导航不放操作按钮。“评论”与“复制”“完善食谱”同属围绕当前食谱的动作，放在同一固定区域符合现有页面规则，也保证用户滚到任意步骤时都能立即进入。

## 3. 详情页入口

底部操作区由两项调整为三项：

```text
┌────────────────────────────────────┐
│ [评论 3]  [复制]  [   完善食谱   ] │
└────────────────────────────────────┘
```

- `评论` 和 `复制` 使用紧凑的次级按钮，保留线性图标与文字。
- `完善食谱` 仍是唯一陶土橙主按钮，视觉优先级不变。
- 没有评论时显示 `评论`，有评论时显示 `评论 3`，超过 99 条显示 `99+`。
- 评论数量来自食谱上的轻量计数字段，详情页不为显示数量额外请求评论列表。
- 不在标题区、右上角或正文中重复放第二个评论入口。

这里刻意不展示“最新评论预览”。一句脱离上下文的评论既可能误导，也会重新把讨论内容带回正文。

## 4. 评论页

### 4.1 页面结构

```text
返回          评论
          山药牛肉末软粥

妈妈 · 今天 09:40
牛肉最后焖 4 分钟是不是也够？
                         ···

爸爸 · 今天 10:12
我试过 4 分钟，中间还是有点红，5 分钟更稳。

────────────────────────
[ 写下问题或这次尝试…… ] [发送]
```

- 导航标题为 `评论`，副标题显示食谱名称。
- 顶部提供 `最新 / 最旧` 排序切换；默认 `最新`，新评论在前。
- 切换到 `最旧` 后，旧评论在前；排序由服务端返回，避免客户端与云端顺序不一致。
- 输入区固定在底部，正文列表独立滚动。
- 空状态文案为：`还没有评论，写下这次尝试，或者想问家人的问题。`
- 评论使用现有家庭成员头像、暖米色底色、深色正文和低强调时间信息。
- 评论不是聊天气泡，不区分左右两侧，避免变成即时通讯界面；每条都按家庭记录的阅读方式左对齐。

### 4.2 编辑与删除

低频管理操作不常驻为多个文字按钮：

- 自己的评论右上角显示低强调 `···`，操作项为 `编辑`、`删除`。
- 管理员查看他人评论时显示 `···`，操作项只有 `删除`。
- 普通成员查看他人评论时不显示操作入口。
- 管理员不能编辑他人的评论，避免改变他人原意。
- 编辑时复用底部输入区，显示 `正在编辑评论` 和 `取消`，主按钮改为 `保存`。
- 编辑后的评论显示 `已编辑`，保留原发布时间。
- 删除前二次确认；首版删除后不显示“该评论已删除”的占位行。

### 4.3 首版文字规则

- 只支持纯文字，每条最多 500 字。
- 不支持评论图片、回复层级、点赞、@成员、表情回应和消息通知。
- 评论针对整份食谱，不做“对某一步评论”；需要说明步骤时直接写“第 3 步”。
- 待补条目也允许讨论，评论本身不能替代成功关键。

## 5. 权限边界

| 操作 | 评论作者 | 普通家庭成员 | 家庭管理员 |
| --- | --- | --- | --- |
| 查看家庭评论 | 是 | 是 | 是 |
| 发布评论 | 是 | 是 | 是 |
| 编辑自己的评论 | 是 | 否 | 仅自己的 |
| 删除自己的评论 | 是 | 否 | 是 |
| 删除他人的评论 | 否 | 否 | 是 |
| 编辑他人的评论 | 否 | 否 | 否 |

所有权限在云函数中按当前微信身份和有效家庭成员资格重新判断，客户端展示状态不能作为授权依据。被移出的成员不能继续查看或操作评论；其历史评论仍显示原家庭称谓。

## 6. 数据模型

评论使用独立集合 `recipe_comments`，不嵌入 `recipes`：

```ts
interface RecipeComment {
  id: string
  familyId: string
  recipeId: string
  authorMemberId: string
  content: string
  createdAt: string
  updatedAt: string
  version: number
}
```

食谱文档只增加：

```ts
commentCount?: number
```

独立集合的原因：

- 评论创建、编辑和删除不应产生食谱修订记录。
- 评论活动不应改变食谱的 `updatedAt` 或乐观并发 `version`。
- 评论增长不能继续放大已经包含修订快照的食谱文档。
- 单条评论可以独立校验作者、版本和删除权限。

删除首版采用物理删除。家庭场景暂不建设审核记录或删除恢复；删除成功后在同一事务中递减 `commentCount`，不能减到负数。

## 7. 云函数接口

```text
recipeComment.list
recipeComment.create
recipeComment.update
recipeComment.delete
```

- `list`：确认当前成员仍属于食谱家庭，再按“最新 / 最旧”返回评论；作者称谓从家庭成员快照解析。
- `create`：验证 1–500 字纯文本，创建评论并增加食谱评论数。
- `update`：仅作者本人可修改，使用评论 `expectedVersion` 防止多设备覆盖。
- `delete`：作者本人或家庭管理员可删除，并安全递减计数。

评论接口独立于食谱 `expectedVersion`，家人发表评论不会导致正在编辑食谱的人遇到版本冲突。

## 8. 一致性与失败处理

- 发布失败时保留输入内容，并明确提示重试。
- 编辑失败时保留编辑态，不把服务端旧内容误显示为已保存。
- 删除失败时评论仍留在列表中。
- 评论数只在创建或删除成功后更新；若计数与实际评论偶发不一致，以评论集合为准，后续可增加校准任务。
- 食谱移入废纸篓后，评论随食谱一起不可访问，但首版不额外删除评论。
- 评论不会进入复制出的食谱；副本从 0 条讨论开始。
- 恢复食谱旧修订不会恢复或回滚评论，因为讨论不属于正文版本。

## 9. 首版验收场景

- 无评论食谱的正文长度和信息顺序完全不变。
- 从详情页任意滚动位置都能进入评论。
- 家庭成员发布评论后，列表和详情入口数量同步更新。
- 作者可以编辑、删除自己的评论，不能操作他人评论。
- 管理员可以删除他人评论，但不能编辑。
- 普通成员看不到他人评论的管理入口，伪造请求仍被云函数拒绝。
- 评论发布或编辑失败时，输入文字不会丢失。
- 评论操作不会创建食谱修订，也不会引发食谱版本冲突。
- 复制食谱不复制评论；恢复修订不改变评论。
- 被移出的成员不能继续访问评论，旧评论仍能显示原称谓。
