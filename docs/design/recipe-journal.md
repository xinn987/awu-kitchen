# 食记首版设计

## 1. 设计结论

“食记”记录某份食谱被实际制作后的宝宝反馈，目的是积累改进食谱的证据，而不是建立每日打卡、用餐日记或营养管理系统。

- 主导航使用独立 `食记` 栏目，页面标题为 `食谱记录`。
- `记一次` 是食记内的动作；中央加号仍只负责新增或导入食谱。
- 每条记录必须属于一份食谱，只收集日期、接受程度、是否按原食谱、可选调整说明和成员归因。
- 记录不会自动修改食谱；家人确认有价值的经验后，仍需通过“完善食谱”形成正式修订。

## 2. 最小交互

接受程度只有三档：`很喜欢 / 能接受 / 不太接受`，不换算成分数、百分比或营养评价。新记录不默认代选，用户必须明确选择一次，避免为了快速保存而积累失真的中间档数据。

默认选择“按原食谱”。只有选择“有调整”时才填写一段不超过 120 字的说明，不重新确认食材、用量和步骤。日期默认今天，允许补记过去日期，不允许未来日期。

记录表单使用明确的食谱和日期选择字段；接受程度使用三张等宽圆角选择卡，并以同一品牌色表达选中，不使用红黄绿评分色。食谱选择复用底部选择器并支持按食谱名或食材搜索。

食记首页按食谱聚合。每次记录是一根竖条，按时间从左到右排列：

- 很喜欢：较高的陶土色竖条；
- 能接受：中等高度的暖沙色竖条；
- 不太接受：较短的灰棕色竖条。

高度和颜色同时编码，避免只依赖颜色。竖条只对应真实记录，不补空日期，也不展示连续天数、目标、趋势分或完成率。点击竖条可以查看并在权限允许时编辑该次记录。

## 3. 数据与权限

记录独立存入 `recipe_attempts`，不嵌入会持续增长的食谱文档：

```ts
interface RecipeAttempt {
  id: string
  familyId: string
  recipeId: string
  recipeName: string
  recipeVersion: number
  occurredOn: string
  acceptance: 'loved' | 'accepted' | 'rejected'
  followedOriginal: boolean
  adjustmentNote: string
  authorMemberId: string
  createdAt: string
  updatedAt: string
  version: number
}
```

`recipeName` 和 `recipeVersion` 是记录发生时的轻量快照，食谱后续改名或修订不会改变旧记录语境。食材和步骤不复制，避免维护第二套正文。

所有有效家庭成员可查看和新增记录。作者可以编辑自己的记录；作者或管理员可以删除。云函数根据微信身份重新校验家庭、作者和乐观并发版本，客户端状态不作为授权依据。

## 4. 首版不做

- 日历、连续打卡、提醒、目标或徽章；
- 每日摄入种类、克数、热量和营养评分；
- 每次重新录入实际食材和完整步骤；
- 自动分析趋势或自动改写食谱；
- 将中央新增食谱入口改为通用记录入口。

## 5. 验收边界

- 新记录默认今天、按原食谱，并能在少量点击内完成。
- 食谱与接受程度都必须明确选择；未填写时在对应字段旁显示行内错误。
- 选择“有调整”后必须填写简短说明；保存为“按原食谱”时云端会清空说明。
- 食记首页只按食谱聚合真实记录，并能从竖条进入单次详情。
- 食谱详情末尾提供“最近记录”轻引用，但成功关键、食材和步骤仍保持更高优先级。
- 创建或更新成功后先写入客户端内存缓存，返回食记首页和食谱详情时立即回显，再后台刷新云端；请求失败不能伪装成空状态。
- 创建、修改或删除记录都不会改变食谱正文、更新时间、版本和修订历史。
